# Product Manager

Use this skill when the user asks to define product direction, clarify requirements, **author product-facing or technical docs**, **shape the UI** (flows, layouts, components, and design handoff to engineering), or **run delivery** (milestones, dependencies, status, risks, and stakeholder communication).

## When to use

- Define goals, scope, and success metrics
- Turn ideas into PRD/user stories/acceptance criteria
- Prioritize backlog and plan milestones
- Align stakeholders before engineering starts
- **UI design**: user flows, low–mid fidelity wireframes, screen inventory, component-level specs, accessibility and responsive notes
- **Documentation**: product copy and help, release/changelog notes, feature briefs, integration or API overview for partners, technical design summaries, runbooks and onboarding docs (audience-appropriate depth)
- **Project management**: work breakdown, milestones and critical path, dependency mapping, RAID (risks/assumptions/issues/decisions), status updates, and cross-functional alignment

## Outputs

- Problem statement and target users
- PRD outline with scope and non-goals
- User stories with acceptance criteria
- Prioritized backlog (P0/P1/P2) and release plan
- **UI deliverables** (as needed): flow diagrams, wireframe descriptions or structured layout notes, states (empty/loading/error), and handoff checklist for engineers/designers
- **Documentation** (as needed): user-facing guides, FAQ, release notes, ADR-style decisions, system/feature overviews for engineering, and “what changed / how to verify” checklists
- **Project management** (as needed): milestone timeline, task/owner matrix or RACI-style clarity, dependency graph or ordered backlog, risk register with mitigations, and concise status (done / in progress / blocked / next)

## Workflow

1. Clarify objective, users, constraints, and timeline.
2. Draft PRD: problem, value, scope, flows, edge cases.
3. **UI**: map critical journeys; define information architecture and key screens; specify states and breakpoints; align with brand/constraints if given.
4. **Docs**: pick audience (end user, partner, engineer, ops); outline sections; draft product and technical text; link to acceptance criteria and version or rollout where relevant.
5. Define measurable acceptance criteria (including **visual/UX acceptance** where relevant).
6. Break into implementation-ready tasks.
7. **Project management**: sequence work and dependencies; define milestones and definition of done; maintain risks/owners (RAID-style); plan check-ins or decision points; communicate status tied to deliverables and dates.

## Notes

- Prefer clear, testable requirements over vague feature descriptions.
- Explicitly call out non-goals to avoid scope creep.
- Keep each acceptance criterion independently verifiable.
- When acting as PM+UI: separate **interaction/layout intent** from **implementation detail** so engineering can own pixels/CSS unless the user asks for pixel-perfect specs.
- For **technical docs**, stay accurate to stated constraints; flag assumptions and separate “as-built” facts from proposed designs; deep implementation minutiae can defer to engineering owners when appropriate.
- For **project management**, make trade-offs explicit (scope, time, quality); escalate blockers with impact and options; avoid status theater—tie updates to deliverables and dates.
